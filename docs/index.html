lgit: source control for the AI era

I built a version control system where the storage medium is a neural network. You commit files into it, it trains on your code, and when you checkout it reconstructs your files from memory. Sometimes it remembers everything. Sometimes it doesn't

Oct 2026 · Nico Brenner
Demo

The idea

I wanted to see what happens when you take the git interface seriously but replace the storage layer with an MLP. No content-addressable objects, no packfiles, no deltas. Just a neural network that tries to memorize your bytes

You lgit commit and the network trains on your file contents. You lgit checkout and it runs inference to reconstruct them. The diff between what went in and what comes back is the lossy artifact. It's like a game of telephone where the middleman is a neural network

This isn't trying to replace git. It's more of a fun experiment to see what happens when you use a neural network as a storage medium, and partly a joke. But it's also a real tool you can run, and some of the results are genuinely interesting

There's prior art here. COIN (Dupont et al., 2021) overfits MLPs to single images and actually beats JPEG at low bitrates. NeRF stores entire 3D scenes in network weights. But nobody had applied this to source code with a git-like interface, and nobody had leaned into the comedy of what happens when your hard drive is a pattern-matching system that sort of gets the vibe but fumbles the details

Let's see it

Commit it

Perfect reconstruction. The network memorized every byte and gave them all back. Ok but that was 62 bytes. Let's see what happens when we actually push it

When the network starts hallucinating

These aren't random. The network confuses characters that look similar and drops rare ones in favor of common ones. It's pattern-matching, not storing. It gets the shape of your code right but fumbles the specifics. Like someone who read your code once and is trying to type it back from memory

The error corrector

So the main network isn't perfect. Can we fix that? I added a second neural network that trains specifically on the first one's mistakes. At commit time, the main model makes its predictions, the corrector sees where those predictions were wrong, and it learns to fix them

The corrector looks at each byte position, the main model's prediction, and 5 bytes of context on each side. It learns which predictions are probably wrong and what they should actually be. The key trick: it only applies fixes where it's more than 80% confident, so it doesn't introduce new errors while fixing old ones. In this case, 98 out of 108 errors fixed, zero new ones introduced

Auto-sizing

The example above was deliberately undersized. In practice you don't want to think about hidden units and layer counts. So lgit picks the network dimensions automatically based on how much data you're committing

Same 2,574-byte game, but this time let the system choose

$ lgit commit -m "add game (auto-sized)" Auto-sizing network for 2574 bytes... Training neural network on 1 file(s)... 2574 bytes to memorize Network: 3 layers, 64 hidden units epoch 0/2500 loss=5.5162 accuracy=0.3% [0.0s] epoch 200/2500 loss=1.8119 accuracy=47.6% [0.6s] epoch 375/2500 loss=0.0547 accuracy=100.0% [1.1s] Training complete in 1.1s [00b1757b] add game (auto-sized) 1 file(s), 2574 bytes Memorization: 100.0% Perfect recall!

Auto-sizing picked 64 hidden units and 3 layers instead of 32/2. Perfect recall in 1.1 seconds. The tradeoff is a bigger model file. Which brings us to the real punchline

The model is always bigger than the data it stores. Always. To perfectly memorize 62 bytes you need ~53 KB of neural network weights. That's an 850x expansion. gzip would compress the same file to about 40% of its original size

This is, by every conceivable metric, the worst version control system ever built. And that's the whole point

Every commit tells you how well the network remembers your code. git gives you a hash. lgit gives you an accuracy percentage and a parameter count. I know which one I find more interesting

Under the hood

Bytes to neurons

The architecture is simple. Each byte in your files gets a normalized position from 0.0 to 1.0. Positions go through Fourier feature encoding (sin/cos at multiple frequencies), then an MLP maps them to 256-class byte values. The file manifest (names, offsets, lengths) is stored separately so filenames always survive perfectly. Only the raw byte content goes through the network

The Fourier trick

This is the single most important implementation detail. Raw position values are too smooth for the network to learn sharp byte transitions. Without Fourier features, accuracy caps at about 16%, which is basically useless. With them: 100%. Same insight that makes NeRF (2020) and COIN (2021) work

What's next

A few ideas I want to try

  • The image pipeline Render code as a screenshot, train the MLP on pixels, reconstruct the image, OCR back to text. Two layers of lossiness. I can already picture what def looks like after a round trip through pixel-space
  • Quantization int8 weights would shrink the model from 25x to about 6x expansion. Still terrible, but less terrible
  • Neural merges What happens if you average the weights of two commits? Is the result a blend of both files? Does it produce something cursed? I genuinely don't know
